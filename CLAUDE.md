# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Feedback loop for C64 and VIC-20 development (peers): assemble with ACME -> boot headless VICE (`x64sc` / `xvic`, under `xvfb-run` if available, else a normal window) -> drive it through VICE's binary monitor (TCP) -> read screen RAM / screenshot. Layout:
- `retro/` — framework package: `vice.py` (`Machine` base: monitor protocol, peek/poke, type, screen, gif), `c64.py` (`C64`), `c64u.py` (`C64U(C64)`: real C64 Ultimate via the `c64u` CLI, host from `~/.config/c64u/config.toml`; screenshot/gif re-rendered from DMA (text modes only, no sprites, bundled `retro/chargen.bin`; device has no video stream), no joyport, DMA writes to `$DC00` don't stick; `programs/c64/hello/run_c64u.py`), `vic20.py` (`VIC20(mem=0|8|16)`), `build.py` (`assemble()` ACME, `compile_c()` cl65, `basic()` petcat, `BUILD` dir), re-exported from `retro/__init__.py`.
- `programs/<machine>/<name>/` — `<machine>` = `c64` or `vic20`; one dir per program: `<name>.asm` + `run.py` (assemble, drive VICE, assert/screenshot). Build output goes to `build/<machine>/` (derived from the dir above the program dir). c64: `hello` is the end-to-end check (also tests `reload`), `frames` the checkpoint/warp check (`run_until`, `run_frames`, exact frame counts under warp), `hello_c` the cc65 path, `hello_oscar` the Oscar64 path (`compile_oscar`, installed in `~/.local/oscar64`, see `docs/oscar64.md`), `sprite` the sprite demo (also `sprites()`, `record_gif`), `joy` the memory-byte input demo, `joyport` the real joystick-port demo, `basic` text BASIC via `petcat` (lowercase source), loaded by inject and by monitor autostart (0xDD), plus `lea`, `piano`, `tetris` (port of the VIC-20 one: 2-char multicolour bevel tiles in a RAM charset at `$3000`, SID melody/bass/sfx via a per-frame tick synced to raster 251, raster-bar title, screen shake; run.py checks game state vars since SID regs are write-only). IRQs are off for good (KERNAL `CHROUT` re-enables them, so it has its own `cls`): input is a keyboard-matrix scan (`readin`/`getkey`), agents inject keys via `$033D` (hotkey bits P1 G2 M4 H8) and `$033F` (a letter, for initials) instead of `type()`. Title: left/right picks 1P or 2P versus (P1 joystick port 2, P2 W/A/S/D or joystick port 1; 1-char tiles, 2 boards at `$c000`/`$c300`, garbage rows 1/2/4 for 2/3/4 cleared, shared piece sequence, first to top out loses). The active player's state is the `CTX` block (P1 between frames, P2 in `PC2` and exchanged in for its step); the `BOARD,x` operands are self-modified per player. run.py pokes/peeks P2 only while `$c143` (idle) = 1. Ghost on with both soft-dropping costs ~15% frames. `snake`: solo (3 lives, new obstacle level every 10 apples, top-5 board, RAM only, initials typed via matrix scan `getkey`; H on title shows it; run.py pokes initials since matrix keys can't be injected), vs computer (greedy apple-chasing AI) or 2 players, picked on the title with left/right; heads are sprites gliding between cells (`back = 8*tick/speed` table), SID melody/bass on voices 1-2 (F1 toggles, port-1 fire masked out) and sfx on 3 (software LFSR RNG);  joystick port 2 / W A S D and port 1 / I J K L, any mix of 0-2 joysticks; hires RAM charset tiles (heads/tails/corners per direction), IRQs off with its own keyboard-matrix scan; run.py parks the snakes (huge SPEED, sprites then snap to cells) and forces steps via TICK. `midnight`: Midnight Hollow, 5-level Halloween platformer (story/mockups in its dir): pick Pip or Dr. Nova (SPD/JMP/LUK = walk speed, jump, chance to survive a hit), collect 20 pumpkins (+ golden key in L3) before the HUD clock runs out, candy throw (5 ammo), L5 = single-screen boss (carry 6 pumpkins to lantern slots while a bat swarm circles). KERNAL/BASIC banked out, own raster IRQ at $FFFE splits HUD/playfield/sky bands (writes land in the right border of the line before); bidirectional h-scroll with two screens ($4000/$4400, back one pre-shifted a frame ahead, never in the same frame as the colour-RAM shift), multicolour per-level charsets ($D022 orange everywhere), map column-major at $E000. Monsters activate only when their spawn point is just off screen (x -48..-17 / 312..343 from the camera) so they walk/fly in from an edge; gears/pendulums and single-screen L5 anywhere in view. Assets are ASCII: `gfx/tiles.txt` (stamps, map letters, tile kinds), `gfx/sprites.txt`, `gfx/music.txt`, `levels/l*.txt`; `gen.py` turns them into build/c64/midnight_*.asm (code $0810-$3FFF + $A000-$BFFF under the BASIC ROM, sprites/data $5000-$9FFF). Music: 4 tunes in `gfx/music.txt` (per-step melody + bass, `-` holds a note): intro (boot, intro, title, select, game over), dance (L1-4), boss (L5), theme (ending); `musicto` fades the old one out over 15 frames from the IRQ. Intro: eyes, lightning, MIDNIGHT HOLLOW rises out of the ground (red, gold after the lightning), story typed (the Count, Grandma Hazel), rules, then the title screen. run.py first checks every pumpkin/key/exit is reachable (coarse jump model), then teleports via the game's respawn (poke chkc/chkr, kill) to test pickups, kills, time-out, exit, game over, key door, gear riding, lantern ending; `run.py play` to play. `playthrough.py [pip|nova|both]` (~5 min) finishes the whole game with joystick input only: a frame-exact Python copy of the player physics (incl. gears/pendulums) plans each hop, inputs go through `joyport` one `gameframe` at a time, real state must equal the simulation; fails on a stall (same spot 3x, no item for 3000 frames) or an unreachable item. Pokes only `inv` (enemies) and `tfr` (clock frozen, frames reported vs the limit). Keep its `step()` in sync with `player`/`platland`/`ride` in midnight.asm. vic20: `hello` (all of mem 0/8/16, `-DEXP=<mem>`), `hello_c`, `joyport`, `basic`, `tetris` (unexpanded, joystick; run.py pokes board/piece vars to test clear, game over, restart).
- `build/` — gitignored output (`.prg`, `.png`).

Needs system tools: `acme`, `cc65` (`cl65`), `x64sc` (VICE; macOS: `brew install acme cc65 vice`, tested on 3.10; Linux 3.7.1 also needs `xvfb-run`, used automatically when on PATH), plus Pillow for `screenshot()` (managed by uv; `retro` is installed editable via `uv sync`). Linux only: C64/VIC-20 ROMs must be in `~/.local/share/vice/C64/` / `VIC20/` (brew VICE bundles them).

## Commands

- Full chain test: `uv run programs/c64/hello/run.py` (assembles `hello.asm`, boots, types `q`, writes `build/c64/hello.png`; exits 1 on timeout); VIC-20: `uv run programs/vic20/hello/run.py`
- Run each program: `uv run programs/<machine>/<name>/run.py`
- Assemble only: `acme -f cbm -o build/c64/hello.prg programs/c64/hello/hello.asm`
- VICE stdout/stderr go to `/tmp/vice_<port>.log`. Port is picked free per instance.
- Checkpoints/warp: `uv run programs/c64/frames/run.py` (asserts exact frame counts under warp, prints the speed)
- Sprite demo: `uv run programs/c64/sprite/run.py` (asserts sprite 0 moves in X and Y, writes `build/c64/sprite{1,2}.png`)
- No linter, no pytest suite; each `run.py` is a script; new programs follow the same pattern.

## Architecture / gotchas

- **VIC-20 specifics** (`retro/vic20.py`): `VIC20(mem=0|8|16)` passes `-memory none|8k|16k`. BASIC loads at `$1001` unexpanded, `$1201` with 8K+ (screen then moves to `$1000`), so a PRG is tied to a mem config; `load_prg` fixes BASIC pointers only at that address. Screen geometry/base/colour RAM are read from VIC-I regs `$9000-$9005` (22x23 normally); they are 0 right after power-on (`screen_text()` returns ""). `display-get` for the VIC-I reports no inner area, so `screenshot()` returns the full image including border (no crop). `joyport()` works the same way (device 37, port 1): up/down/left/fire on VIA1 `$9111` bits 2-5, right on VIA2 `$9120` bit 7 (set DDR `$9122` bit 7 to input to read it); verified in `programs/vic20/joyport`. cc65: stock `vic20.cfg` is unexpanded-only and too small for stdio, stock `vic20-32k.cfg` puts the C stack at `$8000` (crashes on 8K/16K); `programs/vic20/hello_c/vic20-8k.cfg` is trimmed to `$4000`. `basic(..., load=0x1001|0x1201)` sets the PRG address. No sprites/`$D0xx`; sound is in the VIC-I (`$900A-$900E`).
- **Machine is paused between commands.** VICE halts the C64 on every monitor command. Emulated time only advances during `resume()`/`run(s)`/`wait(s)`/`run_until`/`run_frames`/`wait_for_text`/`type`. Any peek/screen read freezes it again. A command sent while the machine runs is only seen at the next vsync (once per emulated frame); while stopped, VICE blocks on the socket, so replies are immediate.
- **Warp is the default** (`Machine(warp=True)`, VICE `-warp`). `run(s)` is wall clock and so varies with host speed; `wait(s)` under warp runs exactly `round(s*50)` frames via `run_frames` (without warp it is `run(s)`). `run_frames(n, line=0)` uses a conditional exec checkpoint over `$0000-$FFFF`: stop at the first instruction with `RL == line`, then at the first with `RL != line` (two stops per frame; a single `RL ==` stop would refire on the next instruction). `run_until(addr, end=None, op="exec"|"load"|"store", timeout=10)` stops at an address (a load/store stops after the instruction); False on wall-clock timeout, machine stopped. Hit = CHECKPOINT_INFO event (0x11, id 0xFFFFFFFF, hit=1) then STOPPED (0x62). Stopping at the same raster line every time can keep landing mid-work: to catch a program in a given state, break on it (tetris `idle()` stops on the store to its idle flag). Scripts with a `play` mode, and `lea` (music meant to be heard), pass `warp=False`.
- **PRGs are injected into RAM** (`load_prg` pokes at the load address, then types `RUN`), not autostarted — drive ROMs aren't available, so programs loading from disk won't work. Loads at `$0801` get BASIC pointers (`$2D/$2F/$31`) fixed up. Needs C64 at READY.
- **Agent input convention** (a program must opt in, see `programs/c64/joy`): `joy()` ORs bits into `$033C` (edge-triggered; program clears it after reading), `joy_hold()` sets `$033E` (level). Bits: up 1, down 2, left 4, right 8, fire 16.
- **Real joystick input**: `joyport(*buttons, port=2)` uses the binary monitor's joyport-set (0xA2), which only drives VICE's "joyport I/O simulation" device (type 37), so it first switches `JoyPort<n>Device` to 37 via resource-set. Pins are active low; port 2 reads at `$DC00`, port 1 at `$DC01`. Level-triggered. Works with any program reading the joystick normally. The sim device also pulls the unused lines low (PA5-7 / PB5-7 read 0); on port 1 that fakes key presses on keyboard rows 5-7, so a matrix scanner should drop rows that read low with no column selected (see `snake` `readin`). Keyboard-matrix injection is NOT possible via the monitor (only the KERNAL buffer via `type()`).
- **RUN/STOP+RESTORE with own keyboard scan**: the KERNAL NMI stop test reads `$DC01` without selecting a column and expects `$DC00=$7F`. Programs that scan the matrix themselves and end with `$FF` must point `$0318/9` at a stub that sets `$DC00=$7F` then `jmp $fe47` (tetris, snake).
- `reload(prg)` = hard reset + `load_prg` in the same VICE process; `load_prg` verifies the bytes it poked, except in `ROM_RANGES` (C64: $A000-$BFFF, $D000-$FFFF: pokes there land in RAM but read back as ROM at READY). Keep PRG data out of $D000-$DFFF (I/O gets poked).
- `assemble(src, symbols=path)` also writes ACME's label list; `labels(path)` -> {name: value} (midnight's run.py uses it for run_until/peek by name).
- `type()` chunks to 10 keys (KERNAL keyboard buffer size), uppercases unless `raw=True`, `\n` -> CR.
- `screen_text()` reads screen RAM at the VIC bank/`$D018` base; graphics chars render as `#`. Use `screenshot()` for sprites/colours/graphics.
- `screenshot()` has VICE 3.7.1 workarounds (crop verified still correct on 3.10): Y offset is off by one (`yo -= 1`) and the pixel buffer comes back a few bytes short (zero-padded). Revisit if VICE is upgraded.
- `stop()` kills the whole process group (xvfb-run, Xvfb, x64sc share it).
- `programs/c64/hello/hello.asm` uses ACME syntax: `!pet` for PETSCII text, anonymous `-`/`+` labels, BASIC stub `10 SYS 2064` at `$0801`, code at `$0810`.

## Working on the framework

- Every framework capability gets a `programs/<name>/` program plus a `run.py` that asserts it end to end (a tiny asm program that mirrors the register/byte under test into screen RAM works well). A monitor command returning OK does not mean it did anything: `joyport` was accepted for a plain joystick yet had no effect until the device type was switched.
- VIC-20 memory map / register reference: `docs/mapping-vic20.txt` (PRG appendix, OCR-corrected, plus a few verified decode notes at the end). Small (~480 lines), fine to read whole. No "Mapping the VIC" scan found.
- C64 memory map / register reference: `docs/mapping-c64.txt` ("Mapping the Commodore 64", 526KB). Too big to read whole; grep it by address or name (e.g. `D015`, `53269`, `SPRITE`) and read only the matching range.
- VICE docs are not installed by brew. For monitor capabilities, read the upstream `vice/doc/vice.texi` (binary monitor chapter) and `vice/src/monitor/monitor_binary.c` from github.com/VICE-Team/svn-mirror; the command's C handler shows what it actually does.
- Deliberately not built (judged over-scope vs. github.com/dexmac221/C64AIToolChain): VLM screenshot analysis (read `screenshot()` PNGs directly), the System 1/2 agent control loop, per-game shell launchers. Not yet built, add when a program needs them: asset pipeline (sprite sheets, image-to-sprite), cycle/frame-loss profiling, scheduled monitor commands during GIF recording.
